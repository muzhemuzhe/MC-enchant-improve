# 第一轮任务：让 3×3×2 真正合体

请先阅读根目录 README.md、AGENTS.md、docs/DESIGN_NOTES.md、docs/SOURCE_RESEARCH.md。

## 目标

创建一个实际能进游戏验证的 Minecraft Java 26.1.2 / Fabric 模组 `Better Enchant`，模组 ID 暂定 `better_enchant`。第一轮只完成：

> 玩家按临时模板放置 18 个原版方块，激活中央附魔台后，18 格转化为视觉上一体的大型机器；拆掉任意机器部件后，其他部件可以正确恢复为原方块（或遵循明确且无复制的生存掉落规则）；保存退出、重进游戏后仍能正确识别。

这不是制作魔法祭坛、材料注魔、合成新装备，也不是实现附魔等级算法的任务。绝对不要提前实现这些。

## 开始方式

1. 在当前仓库创建真实 Fabric 项目，不要把现有 docs/ 和 prompts/ 覆盖掉。以官方 Fabric 26.1.2 模板或当前对应 example-mod 为基础。JDK25；确认兼容的 Gradle/Fabric Loom/Loader/API 版本；官方无混淆映射。项目可使用 Java。
2. 首先确认构建可运行：Windows 用 `gradlew.bat build`，并尽可能用 `gradlew.bat runClient` 做游戏内验收。记录 JDK/Gradle/版本与运行结果到 `docs/DEVLOG.md`。若构建/运行失败，必须把错误和未完成事项明确保留，而不是声称通过。
3. 用 docs/DESIGN_NOTES.md 的临时模板设计 formation/disassembly；别把配方硬编码进 UI。允许四水平方向；位置相对旋转；校验不自动加载区块。
4. 交互暂定“潜行+空手右击中央附魔台”尝试形成。形成后右键 controller 可以显示形成状态（开发期文字反馈即可）。原版附魔在形成之后如何保留/接管，属于下一阶段，先不要试图实现半成品 GUI。
5. 形成态 **不是 18 块未经修改的原版方块**：要确实替换成多方块机器部件；使用 JSON 分段模型以及原版纹理引用做出**连贯的整体外观**，让玩家肉眼可见组装前/组装后差异。后面再做贴图、复杂几何与动画。性能上静态部分避免逐帧动态渲染。
6. 数据模型明确 controller、formed part、世界朝向、每个 part 的 local offset、原始块状态。所有形成和拆除仅由服务端控制，防重复触发、错位拆除和掉落复制。注意放置方块会触发邻居事件，避免形成/解体事件递归；跨区块、爆炸、创造模式和中途存档必须处理或记录明确已知限制。
7. 先实现 18 位置匹配单元测试，之后游戏内运行测试；缺少测试时明确说明不能全面验收。
8. 不要依赖 Immersive Engineering 或 Meridian 作为运行时前置。参考它们只是为了理解实现思路，严禁照搬源码和美术资源。

## 你必须交付

- 完整可运行的 Fabric 工程和资源文件（包括 gradlew、Windows wrapper 和准确的版本配置）。
- 在 `docs/DEVLOG.md` 记录命令、实际成功/失败、截图需求、局限和下一步。
- 在 README 中给出游戏内的搭建方式及测试步骤。
- 一次清晰的 Git commit（使用本地 Git 配置的作者，不添加额外署名），**不要 push**。

## 交付验收清单

- [ ] 18 格完整时形成机器，缺一格不形成。
- [ ] 机器使用分段外观，看上去是整体，不只是原版纹理原样堆放。
- [ ] 四个水平方向下都可以正确形成。
- [ ] 重复激活不会复制方块或者产生第二台机器。
- [ ] 破坏任意 part 后能正确处理剩余部件及掉落。
- [ ] 保存退出重进后，形成/拆解功能仍正常。
- [ ] `gradlew.bat build` 成功。
- [ ] `gradlew.bat runClient` 能启动并测试（如果受环境限制，写清实际情况）。

## 明确禁止

- 不要先实现指定附魔、经验经济、概率加权或宝藏附魔；我们还没敲定机制。
- 不要把高级附魔硬锁在高等级机器；这与设计目标相反。
- 不要偷偷把实际建造流程替换为指令刷出模型。
- 不要擅自上传到 GitHub 或创建仓库。
